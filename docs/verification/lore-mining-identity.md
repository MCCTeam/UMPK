# Lore and held mining identity

## Behavior

Native component-era mining compares the effective held item components when it decides whether to keep an existing destroy target. Equal Lore lines retain progress when a fresh inventory packet creates new list objects. Different text, style, children, line order or line count resets that target. Every vanilla item has an empty Lore default; an explicit removal differs from that default. UMPK's bounded item prototypes omit this default, so the identity owner now normalizes it before the existing effective-map shortcut.

The Client change covers protocols 766–777 through `VanillaMiningItemIdentity` and the existing `InteractionActions.Mining` caller. It preserves the Boolean compatibility wrapper and adds an internal nullable comparison. Received primitive argument kinds that the public text model loses remain unknown; the existing unavailable-request path aborts held mining without inventing a new attack. The same original object remains a proven match. Public APIs, Game/Text models, dependencies, datasets and DI lifetimes are unchanged.
